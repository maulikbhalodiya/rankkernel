# Audit: Breadcrumbs Module (RankKernel)

Scope: `src/Modules/Breadcrumbs/` (TrailBuilder, Renderer, Item, BreadcrumbsSettings, BreadcrumbsModule, functions, template-tags, blocks/BreadcrumbsBlock + blocks/breadcrumbs/), `src/Modules/Schema/Pieces/BreadcrumbPiece.php`, admin settings surface, all `tests/Unit/Breadcrumbs*.php`, and the claimed state in `docs/ROADMAP.md` (2.3) and `docs/competitor-analysis/feature-parity-matrix.md`. Method: source read + test read; `vendor/bin/phpunit --filter Breadcrumb` = **OK, 151 tests, 381 assertions**. No source or test files were modified.

---

## Verdict

The Breadcrumbs module is real and largely matches the roadmap's DONE list: a single canonical `TrailBuilder` produces context-aware trails for home, front page, blog index, post, hierarchical page, attachment, term/taxonomy, CPT archive, author, date, search, 404, and pagination (`src/Modules/Breadcrumbs/TrailBuilder.php:71-103`); a scoped `Renderer` emits accessible `nav`/`ol`/`aria-current` markup with disciplined escaping (`Renderer.php:40-117,161-195`); the shortcode, PHP tag, and server-rendered block all delegate to the same builder (`BreadcrumbsModule.php:241-298`, `functions.php:31-70`, `blocks/BreadcrumbsBlock.php:158-218`); the schema `BreadcrumbList` is built from the *same* `TrailBuilder` through `BreadcrumbsModule::buildTrail()`/`filterBreadcrumbTrail()` (`BreadcrumbsModule.php:309-350`, `BreadcrumbPiece.php:76-161`); visibility is applied exactly once in the builder before pagination, and the renderer is explicitly told not to re-apply it (`functions.php:58-63`, `BreadcrumbsBlock.php:192-197`); and the trail is genuinely lazy with zero-query proofs (`BreadcrumbsPerformanceTest.php:245-342`). The material gaps are: (1) the HTML path applies the `rankkernel/breadcrumbs/items` filter and per-placement `show_home`/`show_current` args that the schema path never sees, so a customised HTML trail can diverge from the schema even though the default path is identical — this is the strict-parity gap the audit was asked to hunt; (2) the schema is emitted only for `post`/`term`/`archive`, so search, 404, home and blog-index have an HTML trail but no `BreadcrumbList` (`BreadcrumbPiece.php:62-68`); (3) there is no guard against duplicate HTML when a page places the block, the shortcode, and the template tag simultaneously. The advertised per-post primary-term gap is real and correctly marked PARTIAL in the matrix: the architecture supports a per-*post-type* primary taxonomy but has no per-post term selection, and term ordering is mechanical (`term_id` ascending).

## HTML and schema trail parity

**Yes for the canonical ancestor trail on every context that emits schema, but No as a strict guarantee.** Both the HTML trail and the `BreadcrumbList` are produced by the same `TrailBuilder::build()` from the same `Context` and the same settings, so the canonical crumb sequence is identical by construction. The guaranteeing code is `BreadcrumbsModule::buildTrail()` (`src/Modules/Breadcrumbs/BreadcrumbsModule.php:309-311`), which `filterBreadcrumbTrail()` calls at `BreadcrumbsModule.php:330`, versus the HTML callers `functions.php:42-50` and `blocks/BreadcrumbsBlock.php:182-190` — all instantiate `new TrailBuilder(...)` over the same shared items. Proven by `BreadcrumbsSchemaIntegrationTest::test_visible_and_schema_trails_share_canonical_items` (`tests/Unit/BreadcrumbsSchemaIntegrationTest.php:426-454`) and `BreadcrumbsTrailBuilderTest::test_filtered_taxonomy_keeps_visible_and_schema_identical` (`tests/Unit/BreadcrumbsTrailBuilderTest.php:1275-1291`). The only differences are deliberate `schemaExcluded` pagination items (`Item.php:22-36`; dropped at `BreadcrumbsModule.php:338-341`; asserted at `BreadcrumbsSchemaIntegrationTest.php:459-491`). However, strict parity is **not** enforced: the HTML path alone applies `rankkernel/breadcrumbs/items` (`functions.php:181-191`) and per-placement `show_home`/`show_current` overrides (`functions.php:44-49`; `BreadcrumbsBlock.php:182-189`), while the schema path uses only stored settings. A site that hides home via the shortcode/block or rewrites items via the filter therefore renders HTML without Home while the schema still contains Home — a genuine divergence under an opt-in context. The schema also covers only `post`/`term`/`archive` (`BreadcrumbPiece.php:62-68`), so search, 404, home and blog-index produce HTML-only trails.

## Matrix overstatement check

The matrix is mostly honest, not overstated, but glosses two things.

1. Row "Schema type: BreadcrumbList" = **DONE** (`feature-parity-matrix.md:188`). Accurate as a type, but the piece is conditionally emitted only for `post`/`term`/`archive` (`BreadcrumbPiece.php:62-68`); search/404/home/blog-index have no schema. "DONE" is defensible at type granularity but hides the coverage gap.
2. Row "Breadcrumbs output plus BreadcrumbList" = **DONE** (`feature-parity-matrix.md:283`). The output and schema pieces exist, but the row's "no cost" note omits that HTML and schema can diverge via the HTML-only items filter/args and that there is no duplicate-output guard across the three placement methods. Overstated only in the sense of implying strict parity.
3. Row "Breadcrumb primary category or taxonomy control" = **PARTIAL** (`feature-parity-matrix.md:284`). This is correctly downgraded and matches the code: per-post-term control does not exist.
4. `ROADMAP.md` §2.3 (lines ~97-105) claims context-aware single/archive/search/404 and "only builds when requested or when Schema's BreadcrumbList piece needs it". The lazy claim is true; the schema-reuse claim is true for the canonical trail only; search/404 are HTML-only. The roadmap's settings list (separator, home label, hide-on-front-page) actually *understates* the shipped surface (show_home, show_current, show_blog_page, show_ancestors, primary taxonomy also exist).

Net: no matrix row is falsely DONE — the per-post-term gap is already PARTIAL — but the DONE rows understate the schema coverage limit and the parity caveats.

## Gap classification

- **P0 (per the audit parity rule): HTML-only divergence vectors.** `rankkernel/breadcrumbs/items` (`functions.php:183`) and per-placement `show_home`/`show_current` (`functions.php:44-49`, `BreadcrumbsBlock.php:173-188`) mutate only the visible trail; no code re-uses the filtered item list for schema, so the schema can present a different trail from a customised HTML trail. Calibration: the default settings path is identical and test-proven, so this is reachable only through opt-in display APIs — if the team treats those as display-only, this should be re-rated P1.
- **P2: Schema coverage gap.** `BreadcrumbPiece::isNeeded()` (`BreadcrumbPiece.php:62-68`) emits `BreadcrumbList` only for `post`/`term`/`archive`; search, 404, home/blog-index render a visible trail with no schema and no test asserts the intended policy for those contexts beyond 404.
- **P2: Per-post primary term is absent.** The architecture supports per-*post-type* taxonomy only (`BreadcrumbsSettings.php:298-321`), and the matrix already marks it PARTIAL (`feature-parity-matrix.md:284`); competitors expose a per-post selector.
- **P3: No term preference ordering.** `postTerms()` picks the lowest `term_id` (`TrailBuilder.php:875-880`); there is no order setting and no dedicated filter for term choice (only the per-type taxonomy filter).
- **P3: No duplicate-output guard.** Block, shortcode, and tag each render independently with `supports.multiple: true`; standard for WP plugins, but no prevention exists if the audit expects it.
- **P3: Fallback label drift when the module is disabled.** `BreadcrumbPiece::build()` falls back to `siteName` for the home crumb (`BreadcrumbPiece.php:79-84`) whereas the module uses `home_label`; only observable while the module is off (`BreadcrumbsModuleTest::test_disabled_module_keeps_fallback_piece_behavior` at :297), so harmless.

No unintended default-context divergence of the ancestor chain was found; the P0 above is bounded to opt-in display APIs.

## Tests that would be needed

1. **Parity under the items filter:** assert that when a filter adds/removes an item on `rankkernel/breadcrumbs/items`, `filterBreadcrumbTrail()` output still matches `buildTrail()` (i.e., define and lock the intended policy) — currently uncovered.
2. **Parity under per-placement visibility args:** call the shortcode/block with `show_home=false` (or `showCurrentItem=false`) and assert the schema trail either follows or is explicitly documented to ignore it.
3. **Schema coverage matrix:** table-driven `isNeeded()`/`build()` assertions for `search`, `404`, `home` (posts and static), and blog-index, locking whether `BreadcrumbList` is intentionally absent.
4. **Duplicate-output behavior:** place block + shortcode + tag on one request and assert the intended number of `nav.rk-breadcrumbs` elements (or a render-once guard).
5. **Per-term selection:** once a per-post primary-term meta is introduced, tests for storage, sanitisation against the post type's public taxonomies, precedence over the `term_id` sort, and HTML/schema parity of the chosen term.
6. **Term preference filter:** a test for whatever ordering/preference hook is chosen, asserting deterministic branch selection with multiple terms.
7. **Fallback rollback:** a test that a `post` context whose `buildTrail()` returns `[]` yields an empty visible trail and does not silently emit a `home=siteName` schema crumb inconsistent with `home_label`.
8. **Real-query budget on cold caches:** extend `BreadcrumbsPerformanceTest` beyond the counting `wpdb` double with an integration assertion so "zero extra queries" is proven against real WordPress, not only stubs.
